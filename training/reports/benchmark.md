# Browser benchmark (Phase 10)

Generated by `js/bench_report.mjs` from `js/bench_browsers.mjs` runs (`data/bench/`). Each run uses the app's own parser worker (`createParserWorker` → `transformerBackend.ts`, wink words, MST, gated and labeled phrases, alternatives), served by `bench-page/` with the production headers (COOP/COEP) and `/models/*` emulating the R2 route.

**Setup**

- Runs (label: browser, OS, logical cores, `navigator.deviceMemory` in GB as reported by the browser):
  - `chrome`: Chrome 158.0.0.0, macOS, 15 cores, 32 GB; development machine (Apple M5 Pro, 48 GB, AC power).
  - `safari`: Safari 27.0.1, macOS, 8 cores, ? GB; development machine (Apple M5 Pro, 48 GB, AC power).
  - `vm-chrome`: Chrome 158.0.0.0, Windows, 2 cores, 4 GB; client machine (T67).
- Owner: Safari and Chrome only for now.
- Sample: 4945 characters of EWT test text (51 sentences, 960 words; `bench-page/sample.txt`), budget 5 s.
- Cold load: empty model cache, files from a local server (no network time; see download sizes), then init and self-test. Warm load: a fresh page loading from Cache Storage. Parse: one warm-up, then the median of 10.
- Memory: resident memory of the browser's processes sampled every 250 ms from outside, peak minus the idle baseline just before the page opened (Chrome: the test profile's process tree; Safari: the page's new WebContent processes plus GPU and networking process growth; client machines: total working set of the browser's processes from `bench-page/vm-sampler.ps1`, so other open tabs count too). It includes the page, worker, wink-nlp, ONNX Runtime's WASM heap, and GPU-process memory, so it is the device's cost, not only the model's.
- Every reported run kept the page focused and visible (one 0.5 s unfocused sample in the VM's ModernBERT run, with no slowdown). Safari throttles unfocused pages: ModernBERT int8 parses rose from 1.4 s to 4–6 s in an earlier, unfocused pass, which was discarded.
- `vm-chrome` (T67): Windows 11 ARM VM in UTM on the development machine, 4 GB RAM, 2 vCPUs, reached through an SSH tunnel (`localhost`, so cross-origin isolation applies). It shows the effect of memory and core count; each vCPU is an M5 Pro core, so its parse times are still faster than a typical low-end laptop. Its memory is Windows' working set of all Chrome processes, not comparable one-to-one with the macOS RSS growth.

## Cache spike (T31)

The page downloaded each model file like `modelLibrary` will (streamed `fetch` into a Blob), hashed it with one `crypto.subtle.digest('SHA-256')` over the whole file, checked it against `labels.json` → `files`, and stored it in the `transformers-cache` Cache Storage under its absolute `/models/<model>/<file>` URL. The app's worker then loaded the model; the bench server logged every `/models` request during that load.

| Browser | Model (variant) | Largest file (MB) | Hash time (ms) | SHA-256 match | Model files re-fetched during load | Other requests during load | Download + hash peak (GB) |
|---|---|---|---|---|---|---|---|
| safari | deberta_v3_xsmall (fp16) | 144 | 119 | all | none | `labels.json`, `/models/_ort/ort-wasm-simd-threaded.asyncify.wasm`, `/models/_ort/ort-wasm-simd-threaded.asyncify.mjs` | 0.76 |
| safari | modernbert_base (fp16) | 302 | 246 | all | none | `labels.json`, `/models/_ort/ort-wasm-simd-threaded.asyncify.wasm`, `/models/_ort/ort-wasm-simd-threaded.asyncify.mjs` | 1.94 |
| chrome | deberta_v3_xsmall (fp16) | 144 | 86 | all | none | `labels.json`, `/models/_ort/ort-wasm-simd-threaded.asyncify.wasm`, `/models/_ort/ort-wasm-simd-threaded.asyncify.mjs` | 0.77 |
| chrome | modernbert_base (fp16) | 302 | 180 | all | none | `labels.json`, `/models/_ort/ort-wasm-simd-threaded.asyncify.wasm`, `/models/_ort/ort-wasm-simd-threaded.asyncify.mjs` | 1.67 |

Findings:

- **No duplicate download:** Transformers.js 4.3.2 finds files our downloader stored in `transformers-cache` under `/models/<model>/<file>` (it checks that key before fetching). Only `labels.json` (read by our runtime with `fetch`) and ONNX Runtime's WASM (`/models/_ort/…`, cached by Transformers.js in the same cache after the first load) were requested.
- **Whole-file hashing is fine:** `crypto.subtle.digest` on the 302 MB file took ≤ 0.26 s; peak memory while downloading and hashing stayed below the warm parse peak. No streaming hash or file splitting is needed (the file is held once as a Blob and once as an ArrayBuffer while hashing).
- **Private windows:** Chrome's incognito-like Playwright context failed `cache.put` for the 302 MB file ("Unexpected internal error"; small quota). Pre-flight should treat a low `storage.estimate()` quota as blocking for model download.
- **ONNX Runtime WASM must be self-hosted:** by default Transformers.js loads it from cdn.jsdelivr.net; the app now sets `wasmPaths` to `/models/_ort/` (`transformerBackend.ts`). The asyncify `.wasm` is 26.9 MB (over Pages' 25 MiB limit), so it ships through R2 with the models.

## Lower-end device (T67): findings

- **4 GB is enough for int8:** both models loaded and parsed in the 4 GB VM without a crash (Chrome's processes grew by at most 0.9 GB).
- **ModernBERT int8 misses the budget on 2 cores:** 5.2 s median (DeBERTa int8: 1.3 s). On a real low-end laptop (slower cores) it will be slower still, so ModernBERT should not be recommended for devices without fp16 WebGPU.
- **WebGPU without fp16:** the VM exposes WebGPU, but its adapter lacks the `shader-f16` feature, so the fp16 variants fail to load ("The device (webgpu) does not support fp16"; status `failed: unsupported`). Pre-flight must check `shader-f16`, not only `navigator.gpu`, and choose int8 (WASM) on such devices.
